# Claudy local-native Claude login candidate

Explicit `adapterConfig.localClaudeLogin: true` requires operator-owned server environment `PAPERCLIP_LOCAL_CLAUDE_LOGIN_TARGET_JSON`, with exact companyId, agentId, userId, host, uid, home, configDir, model, command and PATH pins. Missing or malformed admission fails closed. Never provide deployment identities in public source or accept these pins from agent configuration. Retain responsible_user Anthropic subscription binding and managed connection history.

Default-home mode only: the admitted configDir must equal `<home>/.claude`; any other configDir fails closed. On macOS an explicit `CLAUDE_CONFIG_DIR`, even one equal to `~/.claude`, selects a different native credential context, so native launches (execution, version check, login, local Test probe) remove `CLAUDE_CONFIG_DIR` from the final child environment after the host merge. Ordinary and managed callers keep their configDir behavior.

No native token is read, exported, copied or stored by Paperclip. The CLI runs the admitted absolute command with the admitted PATH and HOME (so its default config directory), host loader variables stripped at the final spawn, and blank competing provider auth variables. It owns login and refresh. Preparation rejects competing auth in native settings and project settings. Foreign identities, remote/sandbox targets, restricted filesystem/network contexts, managed connections and extra CLI arguments fail closed. Managed execution does not fall back to native login. Task credentials (run JWT), permissions and concurrency are unchanged.

Trusted-local execution: Claudy runs on the operator's own host and account. Beyond the auth isolation above, the native lane uses ordinary Claude CLI behavior: normal runtime MCP servers, skills and settings, and the normal Paperclip API lifecycle (comments and status through the skill's API calls with the run JWT). Unattended tool execution uses the existing `dangerouslySkipPermissions` switch (default true; Claudy's explicit false must be set to true under approval). No native-only CLI restrictions (safe mode, empty setting sources, disabled slash commands, tool allowlists) are added. Optional future hardening, if wanted: a sandboxed filesystem/network scope, or narrower tool permissions, applied the same way for all local agents.

Disposition-only recovery: the repair instruction asks for lifecycle-only updates. Server-side, a repair run's closing message is not auto-posted (and no missing-comment retry is queued) only when all of these hold:
- The run is bound to its own successful source run (same company, agent, issue and episode).
- Recovery recorded the issue's `status_version` when it scheduled the repair (`dispositionRepairIssueStatusVersion`), and the current version is exactly one higher. A database trigger bumps it on every status change, so A→B→A or any extra change breaks this.
- The repair run itself logged a successful `issue.updated` with the current status (normal API write by this run and agent).
- The disposition is durable: done or cancelled, blocked with a blocker relation, unblock descriptor or pending interaction/approval, or in_review backed by such a wait path.

Otherwise the message is shown. Explicit comments the run wrote are always shown (reused, not duplicated). Activity timestamps are not consulted. This is not exactly-once presentation.

Candidate only. Vex reviews exact diff and credential boundary before installation/restart or live activation. Deploy the reviewed source through the existing admitted packaging/service route, preserving service PATH. On Claudy only, under approval: keep `localClaudeLogin=true` and set `dangerouslySkipPermissions=true`. Do not change other agents. Sign in privately through native `claude auth login` only if native auth status is missing. No token/code capture. Recheck provider hello, then run a harmless real-task acceptance.

Rollback: restore the prior exact runtime payload with the existing admitted procedure and set `localClaudeLogin=false` (and the prior `dangerouslySkipPermissions`), preserving binding, model, permissions/concurrency and connection history. Native login is not revoked, deleted or transplanted. No DB migration is introduced.
