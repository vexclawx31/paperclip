# Claudy local-native Claude login candidate

Explicit `adapterConfig.localClaudeLogin: true` requires operator-owned server environment `PAPERCLIP_LOCAL_CLAUDE_LOGIN_TARGET_JSON`, with exact companyId, agentId, userId, host, uid, home, configDir and model pins. Missing or malformed admission fails closed. Never provide deployment identities in public source or accept these pins from agent configuration. Retain responsible_user Anthropic subscription binding and managed connection history.

Default-home mode only: the admitted configDir must equal `<home>/.claude`; any other configDir fails closed. On macOS an explicit `CLAUDE_CONFIG_DIR`, even one equal to `~/.claude`, selects a different native credential context than the default, so native-mode launches (execution, version check, login, local Test probe) remove `CLAUDE_CONFIG_DIR` from the final child environment after the host environment merge, including inherited or configured values. Ordinary and managed callers keep their configDir behavior.

Task writes: native mode keeps Claude's default permission mode, so shell HTTP calls (curl/node) to the Paperclip API are refused before any request.
- **Delivery.** At launch, heartbeat checks the server-resolved effective config: `localClaudeLogin`, `claude_local`, a non-remote target, a run JWT and an issue. It then stamps a capability marker (`paperclipTaskTools`: version, agent, issue) into that running run's server-owned context. Only if the stamp lands does the run receive one MCP server, `paperclip-task` (`POST /api/mcp/task-tools`), authenticated by the run JWT. Later whole-object context writes (adapter-managed runtime services) keep the row's current marker inside the same UPDATE.
- **Endpoint admission.** Every MCP method requires an active task-bound run JWT and the matching marker. Ordinary runs are refused even with a valid JWT.
- **Tools.** Exactly `add_task_comment` and `update_task_status` (in_progress, in_review, blocked, done). The input schemas accept no URL, path, method, header, issue, run, company, owner, attribution or command field. Every call requires an `idempotencyKey`.
- **Blocking.** `blocked` requires an explanatory comment and an `unblockAction`. The action becomes an `unblockDescriptor` owned by the run's own agent.
- **Receipts.** These live in the append-only activity log, never in run JSON, which finalization, liveness and presentation rewrite wholesale. A receipt is a hashed key plus payload digest in an issue activity row, scoped to agent and issue. A retried or recovered run of the same agent therefore replays instead of writing again.
- **Comments.** The comment and its receipt-bearing `issue.comment_added` activity commit in one transaction. That transaction locks and re-checks the running run, current assignee, current execution run, capability and agent status. A retry replays the original result; a different payload with the same key is a conflict.
- **Status changes.** These stay on the authoritative `PATCH /api/issues/:id` route. A pending receipt is reserved under the same locked check before forwarding; definite 4xx rejections append a release. The route's committed status and status version are recorded on success. A lost or aborted forward, or a 5xx, reports an unknown outcome on retry and is never re-sent.
- **Cancellation.** Forwarding is aborted on MCP client disconnect or after 60s. Stop and the reservation serialize under the issue/run locks. The forwarded write is also guarded at its commit by existing core code: the PATCH route passes the authenticated agent and run into `issueService.update`, whose write transaction locks the issue row and calls `assertAgentRunWriteAllowed`. That call locks the run bound to the company and agent and rejects cancelled or cancellation-requested runs. A Stop that commits before the route's commit therefore prevents the status change. Aborting the forward only stops waiting.
- **Permissions.** Only the two `mcp__paperclip-task__*` names are passed to `--allowedTools`, and the effective prompt tells the run to use them instead of curl or node. No Bash rule, command prefix, settings source, bypass flag or sandbox change is added. Ordinary, managed and remote runs never receive the server, the marker, the prompt section or the admission.

Disposition-only recovery: quiet presentation applies only to a server-scheduled legacy disposition repair run that meets all of these conditions:
- It is bound to its own successful source run (same company, agent, issue and episode).
- It holds its own completed task-tool status receipt (same run, agent and issue) whose route-committed `status` and `statusVersion` exactly equal the issue's current ones. A database trigger bumps `status_version` on every status change, so any later transition, including A→B→A, breaks the match. Activity timestamps are not consulted: issue activity is written after the issue commit, so its order is not transition order. With no matching receipt (a crash before the receipt, a non-task-tool lane, a foreign run or agent), the prose is shown.
- That disposition is durable: done or cancelled, blocked with a blocker relation, unblock descriptor or pending interaction/approval, or in_review backed by such a wait path. In that case its closing message is not auto-posted, and no missing-comment retry is queued. Otherwise, including when the repair left the task in todo or in_progress, its final message is presented normally. Explicit comments written by the run are always shown. The withheld message stays in run events, and the decision records its event id.

No native token is read, exported, copied or stored by Paperclip. The CLI uses the admitted HOME (and therefore its default config directory), the admitted absolute command and PATH, with host loader variables stripped at launch, owns login and refresh, and receives blank competing provider auth variables. Managed account execution does not fall back. Foreign identities, remote/sandbox execution, restricted filesystem/network contexts and overriding auth/customization arguments fail closed. Native-mode invocation uses safe-mode plus explicit Paperclip MCP configuration; unrelated host settings/hooks/skills/plugins are not changed or imported. Paperclip task credentials, task permissions and concurrency remain unchanged.
